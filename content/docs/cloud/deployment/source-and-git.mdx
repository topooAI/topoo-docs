Topoo Cloud uses Git as the source-version foundation, but it does not require every customer to operate GitHub directly.

The product model separates three responsibilities:

- a **Git provider** stores repositories, branches, tags, commits, and review history
- **Topoo Source** binds exact repository scopes and revisions to problem-oriented Nodes
- the **Release Controller** validates, integrates, builds, and promotes accepted changes

The canonical objects and editor relationship are defined in [Node Workbench and Lifecycle Model](/docs/cloud/deployment/node-workbench).

GitHub is the first external provider. It is not the Topoo product model and it is not the only long-term source mode.

## Three source-authority modes

Every Project has its own permanent `project_id` and source namespace. Project name, repository name, branch, slug, and domain are labels or bindings; none of them is the Project identity.

| Mode | Source of truth | Customer experience |
|---|---|---|
| Topoo managed | Topoo Source | Create, edit, version, review, and release source inside Topoo. GitHub can be attached later as an optional mirror or delivery target. |
| GitHub managed | GitHub | Keep GitHub as the canonical repository. Topoo imports exact revisions, reconciles provider events, and deploys accepted source. |
| Detached snapshot | Topoo Source Revision | Upload or import an immutable package without maintaining a live provider connection. The Project can later be converted to Topoo managed or connected to GitHub. |

All three modes must produce the same Topoo-facing objects:

- repository identity
- branch or reference
- immutable commit
- source root
- canonical Source Revision
- Submission and Change Summary
- Checks
- immutable Node Version
- optional immutable Node Artifact
- Project Release Candidate
- Release Artifact Set
- Deployment

This common model lets Projects, Nodes, deployments, audit logs, and Agents work consistently regardless of where Git is hosted.

## Repository and Node boundary

Repository and Node are not aliases.

- one repository may supply one Node
- one monorepo may supply several Nodes through different root paths
- one Node may bind multiple source inputs when one responsibility genuinely spans them
- one Project may organize Nodes backed by several repositories

Node topology follows problem ownership, durable attention, and delivery responsibility. Repository layout is only one source input.

Each Node Source Binding must identify the repository, reference policy, primary root path, additional affected paths, required Checks, build contract, Artifact contract, and versioned dependencies. Two Nodes may bind the same repository, but they must not rely on an ambiguous repository-wide identity.

```text
Repository: product-monorepo
├── apps/console   → Console Node
├── apps/api       → API Node
└── packages/ui    → UI System Node
```

If two proposed Nodes own the same source scope, produce the same output, and follow the same version and delivery lifecycle, they are one Node with multiple Agents or linked Sessions rather than two independent Nodes.

Separating a repository is not enough to create a working product boundary. The consumer must reference a real, immutable version or Artifact from the separated responsibility. Two copied packages with no enforced dependency are not a completed split.

## GitHub-first architecture

For a connected GitHub repository:

1. Topoo records the repository and selected branch.
2. Topoo reads the exact commit and imports an immutable source snapshot.
3. Pull Requests become provider evidence attached to Topoo Submissions or Change Requests.
4. GitHub Checks become Topoo Checks.
5. Accepted Submissions produce an immutable Node Version.
6. The Release Controller integrates accepted Node Versions into a Project Release Candidate.
7. Required Node Artifacts are built or resolved and sealed into a Release Artifact Set.
8. Preview and Production promotion reuse that accepted Release Artifact Set.
9. The deployment record preserves Source Revisions, Submissions, Checks, Node Versions, Artifacts, Environment, operator, approval, and time.

GitHub remains the repository source of truth in this mode. Topoo adds the cloud operating model and release ledger around it. A Project may keep deploying a previously captured immutable Source Revision during a temporary GitHub outage.

## Repeated imports create independent Projects

Importing the same GitHub repository more than once creates independent Topoo Projects. Each import receives its own:

- permanent `project_id`
- Topoo source namespace and revision history
- environments, resources, secrets, checks, releases, and rollback history
- generated Preview and Production addresses
- source-authority and synchronization policy

The imports may initially point to the same repository, branch, and commit. They do not share Project identity or deployment state.

Topoo must not create three new GitHub repositories merely because one GitHub repository was imported three times. A provider repository is created only when the user explicitly enables a Topoo-to-GitHub mirror or write-back workflow.

## Bidirectional GitHub synchronization

Bidirectional synchronization is a Project policy, not an automatic side effect of import.

For **GitHub managed** Projects, GitHub changes flow into Topoo through installation permissions, webhooks, reconciliation, and exact-revision import. Topoo changes must be delivered back through an explicit branch, commit, and Pull Request or protected-reference workflow.

For **Topoo managed** Projects, Topoo remains canonical. The user may publish selected branches or releases to a newly created or existing GitHub repository. Provider status is visible as synchronization evidence, not as the Project identity.

Every outbound operation must be idempotent, retryable, auditable, and conflict-aware. Topoo must show the last synchronized revision, pending local and remote changes, rejected provider operations, and the recovery action.

## Repository lifecycle

Project lifecycle and provider-repository lifecycle are separate:

- archiving or deleting an imported Project detaches its provider binding; it does not delete the upstream repository
- deleting a Topoo-created GitHub repository is a separate destructive action with explicit confirmation and audit evidence
- deleting one of several Projects imported from the same repository must not affect the others
- disconnecting GitHub must preserve captured Source Revisions, Artifacts, Deployments, and audit history
- reconnecting must reconcile from recorded cursors rather than silently replacing Topoo state

## Topoo-managed source

Customers who do not use GitHub still need real source-control guarantees.

Topoo-managed source therefore needs a Git-compatible version service, not only a custom table of file drafts. The complete capability includes:

- repository creation and deletion
- clone, fetch, pull, and push
- branches, tags, commits, and history
- authentication and access policy
- change requests and review
- protected branches and required checks
- webhooks or event delivery
- backup, recovery, quotas, and garbage collection
- import from and export to standard Git providers

Topoo can implement this behind the control plane with a proven Git backend. Customers interact with Topoo Projects, Nodes, Change Requests, and Releases rather than the backend vendor.

## Agent submission channels

An Agent must not deploy merely because it changed files.

An Agent works under explicit Node scope. A Work Session is a temporary Project-scoped transaction that may hold one or more Node scopes, while each Node persists identity, permissions, source scope, Submissions, checks, and version history across Sessions.

Each writing Session receives an isolated Git worktree or equivalent copy-on-write Workspace. Provider branches and commits may implement that isolation and history, but Topoo creates and records them ambiently instead of making routine Git mechanics the user workflow.

Every Agent submission enters a channel with explicit authority:

| Channel | Result |
|---|---|
| Draft | Store a proposed change without integration or deployment. |
| Review | Run checks and present the diff for acceptance. |
| Integration | Add an accepted change to a release candidate. |
| Preview | Build an isolated, addressable environment. |
| Production | Promote an approved, immutable release. |

The control plane should show:

- submitting Agent and workspace
- base and head revisions
- files and resources affected
- conflicts with other submissions
- checks and approval state
- included release candidate
- preview and production deployments
- rollback target

Submission authority and deployment authority remain separate.

## Deterministic integration

Multiple Agents may work in parallel, but one deterministic program owns integration:

1. pin the expected base revision
2. accept bounded submissions
3. detect stale bases and overlapping ownership
4. integrate into a single candidate
5. run required checks once against that candidate
6. create one immutable artifact
7. promote only that artifact
8. write the complete release and audit record

This is the fixed integration path behind the visual control plane. It prevents one Agent from overwriting another Agent's accepted work.

## Portability rule

Topoo source must never trap the customer.

A Topoo-managed repository must be exportable as normal Git history. A connected repository must be disconnectable without losing Topoo deployment and audit history. Runtime artifacts remain linked to their exact source revision in every mode.
