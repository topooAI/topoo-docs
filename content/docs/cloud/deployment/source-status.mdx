## Evidence contract

| Layer | Meaning | May mark a capability Completed? |
|---|---|---|
| Source-confirmed | The required implementation exists on the canonical source revision. | No |
| Runtime-verified | The exact production path and state were exercised successfully. | No, unless the full acceptance contract is covered |
| UI accepted | The authenticated customer surface exposes the real state without placeholders or invented data. | No, unless the capability requires UI acceptance and every other gate also passes |
| Canonical audit | The full user outcome and required evidence are written into the stable `V-*` row. | Yes |
| Linear workflow | Work is Backlog, Todo, In Progress, In Review, or Done. | No; it mirrors execution and accepted audit state |

An implementation child may be Done while its parent capability remains Not completed. A milestone percentage is workflow progress, not an independent product-completion claim.

## Product boundaries that remain open

### Agent Control Plane

Deployment, Release, Compute, and Source acceptance do not by themselves deliver invisible multi-Agent coordination.

The separate **Agent Control Plane, Persistent Authorization & Cost Governance** milestone remains not completed. It must provide:

- one durable user grant that safely governs multiple independent external Sessions
- Project- and Node-scoped Agent identity and permissions
- isolated writing Workspaces rather than multiple Sessions sharing one mutable checkout
- bounded model, build, deployment, and retry budgets with circuit breakers
- immediate revocation and auditable credential delivery
- accepted Changes, conflict detection, integration, Preview, Production, and rollback evidence

A Codex plugin may connect a Session. It cannot by itself guarantee local filesystem isolation or Production authority. A supervised local Workspace manager and the Topoo Cloud control plane must enforce those boundaries.

### Observability coverage

The 11 canonical Observability capabilities are accepted. The separate **Observability UI & Platform Coverage** milestone remains not completed because one unified Workspace must continue to bind real telemetry from every other product domain as those domains become available.

The UI must preserve the distinction between real zero, unavailable, and provider error. It must not fabricate a live-looking series.

### Domain control plane

The 10-item Vercel-parity Domains baseline is accepted, including default/custom domains, DNS records, TLS, CDN, routing, cache, image optimization, Edge Config, and wildcard domains.

Broader managed-DNS and agency operations are separate product scope. Linear keeps the two-level Domain navigation, agency account model, delegated-zone journey, audit/history, and complete customer lifecycle as explicit follow-up work rather than inflating the completed baseline.

## Deployment relationship

The accepted Deployment baseline covers history, details, rollback, source-restore boundaries, rolling releases, skew protection, health checks, and release approvals.

The relationship remains:

```text
GitHub Source Revision
→ Build
→ immutable Artifact
→ Environment Deployment
→ health and approval gates
→ Production promotion
→ rollback target and audit evidence
```

Project is the integration and release authority. Node is a permission-scoped code and attention boundary inside a Project; it is not independently operable by default. Work Sessions and Agent Changes feed the Project release path but do not gain Production authority merely by modifying files.
