## Purpose
This document is the board home and architecture index for the `project` module.

It does not try to explain the whole project system in one uninterrupted essay.

Its job is to define:
- what the `toProject` board is for
- which blocks organize the board
- which topics belong to each block
- which pages define each part of the system
- how the reader should move through the board

This page is the reader's map before the detailed docs begin.

## Why This Exists
The project module reached a point where UI refinement alone was no longer enough.

We hit repeated structural drift:
- `Work items` drifting toward timeline/gantt behavior
- `Timeline` and `Work items` sharing rendering assumptions that should have stayed separate
- `Overview`, `Outcome`, `Workstream`, `Tasks`, and `Notes` carrying overlapping meanings
- `Project` itself behaving partly like a task container, partly like a document, and partly like a runtime panel

That made one thing clear:

The missing piece was not another visual pass.

The missing piece was a project-centered architecture contract.

That is why this index exists first.

If we start from isolated sub-documents without restating the argument, the architecture becomes mechanically structured but intellectually thin. The reader can see the folders and headings, but not the reasoning chain that forced the split.

## Core Thesis
`Project` is the git-backed execution container of the agentic platform.

It is not:
- only a runtime panel
- only a task board
- only a document surface
- only a wrapper around an execution engine

It is the root coordination object that organizes:
- outcome
- workstream
- task
- activity
- asset / file
- timeline projection
- runtime state

under an agent-led operating model.

This is the sentence that all other documents are meant to defend, refine, or implement.

## Board Definition
`toProject` is a board, not just a folder of project docs.

As a board, it should do three things at once:
- define the semantic center of project
- explain how project executes
- map that architecture onto the current product surface

That means the board needs internal structure.

The board is not one long article.

It is a system of:
- `board`
- `block`
- `topic`
- `page`

For `toProject`, those layers should be read like this:

- `board`: `toProject`
- `block`: one major architecture lane inside the board
- `topic`: one bounded knowledge concern inside a block
- `page`: the concrete document that explains that topic

## Document Structure
This architecture is intentionally split into focused documents to avoid one oversized, high-context page.

The split is not for its own sake.

We split because the architecture now has two different reading modes:
- a reader trying to understand the whole project-centered thesis
- a reader trying to answer one bounded question, such as git, runtime, or UI mapping

One document cannot do both well without becoming too long and expensive to read.

### 1. Index
- [PROJECT_CORE_STRUCTURE.md](/docs/toproject)
- Purpose: board home, block map, and reading order

### 2. Object Model
- [PROJECT_OBJECT_MODEL.md](/docs/toproject/object-model)
- Focus: `what` the project-centered object model is and `why` it exists
- Reason it is separate: this is the semantic center of the system, and it needs uninterrupted narrative space

### 3. Git Model
- [PROJECT_GIT_MODEL.md](/docs/toproject/git-model)
- Focus: `what` git domains exist, why git is core, and how project binds to them conceptually
- Reason it is separate: git is no longer a tooling footnote; it is part of the project architecture itself

### 4. Runtime Model
- [PROJECT_RUNTIME_MODEL.md](/docs/toproject/runtime-model)
- Focus: `what` the operating layer is, including runtime, execution mode, commands, hooks, automation, and continuity
- Reason it is separate: runtime logic is essential, but if mixed into the object model it will overpower the project-centered thesis

### 5. Execution Architecture
- [PROJECT_EXECUTION_ARCHITECTURE.md](/docs/toproject/execution-architecture)
- Focus: how intent, decomposition, runtime, git, and evidence combine into one operating loop
- Reason it is separate: this is the synthesis doc that turns the individual definition docs into one readable execution system

- [PROJECT_UI_MAPPING.md](/docs/toproject/ui-mapping)

## Reference Position
This architecture is informed by agentic platform engineering references such as the Saul Fernandez model, but it is not a direct copy.

We adopt principles, then extend them locally.

The most important adopted principles are:
- agent intelligence must be treated as infrastructure
- git is the backbone
- intent, execution, and knowledge should be separated
- execution requires explicit operating surfaces

The most important local extensions are:
- `Project` as the primary product object
- `Outcome -> Workstream -> Task` as the core structural chain
- `Activity` as execution evidence
- project-centered UI contracts
- Cloudflare-only runtime assumptions

## Current Direction
The current implementation direction should converge toward:
- project as a git-backed execution container
- Cloudflare as the runtime plane
- outcome, workstream, task, activity, and assets as explicit object surfaces
- overview as a summary surface, not a dumping ground
- work items, board, and timeline as separate projections over the same execution model

In other words:
- object semantics must stay stable
- operating semantics must stay explicit
- UI projections must stay subordinate to both

## Execution Architecture Summary
The `toProject` board should be read as one operating system for delivery.

That means the board is not just where tasks are listed.

It is where five planes are made to work together:
- intent
- decomposition
- operation
- git versioning
- evidence

The canonical chain is:

`Project -> Outcome -> Workstream -> Task -> Activity / Assets`

The operating loop is:

`Intent -> Workstream -> Task -> Runtime -> Git -> Activity -> Updated Project State`

That loop is what makes the board more than a planning tool.

It turns the board into the execution architecture of the product.
